# Decisões do Projeto

# 📌 20 — DECISÕES DO PROJETO (Decision Log)

## 📖 Objetivo

O documento de Decisões do Projeto registra todas as decisões importantes tomadas durante o desenvolvimento do BusinessOS.

Seu objetivo é:

- Documentar o motivo de cada escolha;
- Evitar decisões contraditórias;
- Facilitar manutenção futura;
- Ajudar novos desenvolvedores a entenderem o projeto;
- Servir como histórico arquitetural do sistema.

---

# 🏢 DEC-001 — O Produto será um SaaS Multi-Tenant

## Decisão

O BusinessOS será um único sistema utilizado por várias empresas.

Cada empresa possuirá seus próprios:

- Usuários;
- Clientes;
- Agendamentos;
- Financeiro;
- Landing Page;
- Assinaturas.

---

## Motivo

Permite:

- Escalabilidade;
- Receita recorrente;
- Atualizações centralizadas;
- Menor custo operacional.

---

## Consequência

Todo dado deverá possuir:

```
empresa_id
```

Todas as consultas deverão ser filtradas pela empresa autenticada.

---

# 🔒 DEC-002 — Isolamento via RLS

## Decisão

Implementar Row Level Security (RLS).

---

## Motivo

Garantir que uma empresa nunca consiga acessar dados de outra.

---

## Consequência

Todas as tabelas críticas deverão possuir políticas de acesso.

# 🧱 DEC-016 — Núcleo Multi-Tenant antecipado para Sprint 2

## Data

11/07/2026

## Contexto

A fundação (Sprint 1) e o hardening (Sprint 1.1) foram aprovados. A sequência anterior iniciava Landing Page antes da consolidação completa de workspace multiempresa, convites e permissões.

## Decisão

A Sprint 2 passa oficialmente a ser o **Núcleo Multi-Tenant** com:

- Empresas
- Workspace
- Memberships
- Permissões
- Convites
- Onboarding

## Motivo

Garantir isolamento, segurança e consistência arquitetural antes dos módulos funcionais dependentes.

## Consequências

- Reordenação oficial das próximas sprints.
- Landing, Agendamento, CRM, Financeiro, Dashboard e Assinaturas passam a depender do núcleo concluído.
- Documentação de roadmap/todo/changelog deve permanecer alinhada a essa ordem.

## Status

Aceita

# 🛡️ DEC-017 — Sprint 2.1 obrigatória para hardening antes da Sprint 3

## Data

11/07/2026

## Contexto

Com o Núcleo Multi-Tenant implementado na Sprint 2, foi definida uma etapa dedicada para estabilidade, segurança e qualidade antes da evolução para módulos de negócio públicos.

## Decisão

Executar obrigatoriamente a Sprint 2.1 focada em:

- Hardening técnico sem novas funcionalidades de negócio
- Expansão de cobertura de testes do núcleo
- Auditoria de segurança e isolamento multi-tenant
- Revisão de performance e refatoração controlada
- Validação final com `typecheck`, `lint`, `test` e `build`

## Motivo

Reduzir risco arquitetural acumulado e evitar que a Sprint 3 herde fragilidades de autenticação, autorização, contexto de tenant ou regressões de base.

## Consequências

- Sprint 3 depende da aprovação explícita pós-auditoria da Sprint 2.1.
- Segurança e isolamento tornam-se gates formais de evolução.
- Execuções de `supabase db lint` e testes SQL/RLS passam a ser obrigatórias quando o ambiente local de banco estiver disponível.

## Status

Aceita

# 🧰 DEC-018 — Limitações de infraestrutura local (sem impacto arquitetural)

## Data

11/07/2026

## Contexto

Durante o encerramento da Sprint 2, os gates `supabase db lint`, `supabase test db` e o build local apresentaram bloqueios operacionais no ambiente Windows do desenvolvedor.

## Decisão

Registrar oficialmente que:

1. **Supabase local depende de Docker Desktop** — sem Docker ativo, os comandos `db lint` e `test db` não podem conectar ao Postgres local (`LegacyDbConnectError`).
2. **Erro `EPERM` no build é limitação de ambiente local** — causado por lock de filesystem em pasta sincronizada (OneDrive) no diretório `.next`, sem evidência de risco para produção (Vercel/CI).
3. Essas limitações **não alteram arquitetura, segurança de produção ou contratos do BusinessOS**.

## Motivo

Evitar confundir bloqueios de infraestrutura de desenvolvimento com débito técnico de produto ou arquitetura.

## Consequências

- Gates de banco local tornam-se obrigatórios quando Docker/Supabase local estiver disponível (ou em CI com runner compatível).
- Recomenda-se manter o repositório fora de sincronização OneDrive para artefatos de build, ou excluir `.next` da sincronização.
- A Sprint 2 pode ser encerrada com gates de aplicação completos, mantendo validação SQL/RLS como pendência de infraestrutura local documentada.

## Status

Aceita

# 🛡️ DEC-022 — Preview Landing via RPC SECURITY DEFINER

## Data

11/07/2026

## Decisão

Usuários anônimos acessam preview somente via `get_preview_landing_payload(preview_token, company_slug)`. Tokens são validados por hash; nenhuma leitura direta de tabelas protegidas após validação no cliente anon.

## Motivo

RLS bloqueia leituras diretas de draft para `anon`; RPC centraliza validação e payload sem expor dados de outros tenants.

## Status

Aceita

# 🚫 DEC-023 — Slugs reservados do sistema

## Data

11/07/2026

## Decisão

Slugs como `login`, `dashboard`, `admin`, `api`, etc. são reservados via `is_reserved_slug()` no banco, `RESERVED_PUBLIC_SLUGS` no app e validação Zod em `publicSlugSchema`. `create_company` rejeita slugs reservados.

## Motivo

Evitar colisão entre rotas do app e URLs públicas de tenants.

## Status

Aceita

# 💡 Decisão mais importante do BusinessOS

> **Não construir tudo de uma vez.**
> 

O projeto será desenvolvido de forma incremental:

**Fundação → Hardening → Núcleo Multi-Tenant → Landing Page → Agendamento → CRM → Financeiro → Dashboard → Assinaturas → Painel Administrativo → IA e Automações**

Essa decisão reduz drasticamente a complexidade, facilita testes, permite validação com clientes reais e aumenta muito as chances de transformar o BusinessOS em um SaaS sustentável.
